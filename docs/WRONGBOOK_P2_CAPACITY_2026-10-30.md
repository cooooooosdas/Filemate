# 错题万题并发 P2 修复｜2026-10-30

## 范围

## 原因与修复

原实现按不同日期分组仍由 SQLite 逐项回调 Python，同一页的计数与选页共触发约 8 万次日期解析；四并发时重复取得 Python 锁，时间分布越分散问题越明显。首次 B 探测为 1624.01ms，本轮重新复现也超过原 500ms 门槛。实际耗时受主机负载和线程调度影响，原始样本全部保留，不以不同时间的测量比例承诺固定加速倍数。

本轮 JSON1 分支在当前账号的同一 query_only 快照内：

1. 先应用相同的文本／资料筛选，仅聚合不同的 TEXT 到期字符串；不读取全库题干或答案到 Python。
2. 将日期一次聚合返回后，在 Python 中逐日期严格解析一次，计算原有 UTC 秒数和上海自然日。避免每日期跨越 SQLite/Python 边界，也避免逐行取回游标的竞争。
3. 用一个绑定 JSON 参数建立原生日期关系，保留完整最终筛选、全范围计数和排序，再取有限页。日期键编码为 UTF-8 十六进制，保留 TEXT 索引关联；无用户数据拼接 SQL。
4. 普通到期列表使用左关联，保留无效日期及原 NULL 排序；推荐和预览继续剔除无效日期。BLOB 日期不会继承同字节 TEXT 日期的换算结果。核验只处理所请求的至多 20 题。

日期解析、评分规则、响应形状、认证和资料边界不变；无新的写入、迁移、任务、模型调用或跨账号缓存。无 JSON1 时保留原分支，其容量未由新分支结果替代。

## 已遇到的问题及记录原则

- 第一版只消除了日期函数回调，直接查询通过，但实际 HTTP 暴露了普通到期列表和逐行读取的额外开销；该失败结果保留。
- 随后聚合读取后，推荐／预览通过，推荐搜索仍有 685.85ms 的场景；进一步用共享文本条件提前缩小日期范围，而最终筛选不省略。
- 实际 SQLite 3.26 CLI 发现 JSON1 会截断对象键中的 NUL。已观察旧键不匹配，再以十六进制键修复；7 种分隔符的旧引擎键关联均通过。该 CLI 验证不是生产 Python 全运行时或并发验收。
- 新 NULL 排序测试最初试图写入受 NOT NULL 约束的字段，测试夹具报错。已改为合法存储的空字符串，其解析结果仍是 NULL；没有放宽生产判断。
