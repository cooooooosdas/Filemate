## 已确认事实

现役业务源码fdf6f40、Python3.11.13、SQLite3.26.0。读取上一轮自建的万题合成库（9992种到期时间），不访问生产学习数据；进程nice10，有墙钟上限，不调用模型。读取正确总数9995、页30；此测试库的5条不合格记录不进入推荐。

EXPLAIN QUERY PLAN显示：计数和取页分别物化review_times、创建GROUP BY临时B树，再用自动覆盖索引按raw关联；计数扫描和取页扫描各执行一次。无JSON1路径另有逐行Python校验和日期回调。实际查询计划支持这一定位，不是仅凭历史描述猜测。

## 实验一：合并计数与取页

测试程序在同一只读快照里，将真实生成的SQL改为紧凑picked CTE，使用COUNT(*) OVER()计全范围数量，只在最终取30条详情时读取完整行。原方案和候选SQL均核对实际数量及相同首屏ID顺序。

| 路径 | 原两次SQL四并发P95 ms | 紧凑窗口SQL四并发P95 ms |
|---|---:|---:|
| 原生JSON1 | 1279.38 | 583.97 |
| 强制无JSON1 | 5532.70 | 3034.86 |

每项3次暖请求及20个四并发样本。此实验只计核心SQL，不包含日期关系准备、API认证和结果格式化；即便按这个较窄范围，候选仍超过500ms，因此不能据此宣布容量通过。没有验证空偏移页、全部筛选、损坏日期、所有数据库编译选项或接口兼容性，不进入产品代码。

## 实验二：请求内临时日期索引

诊断程序在同一业务只读快照读取不同日期、按原引擎严格转换，建立独占URI的内存SQLite日期表，并附加到本次只读连接；分批绑定写入的只是内存表，不改业务库。再执行紧凑窗口SQL，回到原表只取30条详情。结束关闭连接；连接内PRAGMA query_only始终为1，附加数据库路径为空（纯内存）。

| 路径 | 包含日期读取／转换、临时表建立及SQL的四并发P95 ms |
|---|---:|
| 原生JSON1 | 586.70 |
| 强制无JSON1 | 1555.48 |

每项3次暖请求及20个四并发样本，真实总数与首屏ID顺序一致。此实验比实验一多计日期准备和连接建立，不能把两张表直接当成同口径加速比例；仍未包含实际HTTP/认证/格式化。两项均未达到500ms目标，**不构成修复或发布验收**。
