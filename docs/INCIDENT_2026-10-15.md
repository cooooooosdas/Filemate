## 00:41 后捕获的新证据与修复

资源记录器捕捉到 API 从约 100 MiB 升至 733 MiB；00:41:04、00:41:57 两次触及 768 MiB cgroup 上限，被内核终止并自动恢复。同期 Nginx 两次 `POST /process` 为 502，上传元数据均为 15,629,558 字节 PDF。没有读取或输出用户文件正文、原名和密钥。此轮 SSH 一直可用，证明防护避免了该 API 峰值拖垮主机；不能反向证明第一次整机失联的唯一根因。

早先合成回归只使用了纯文本 `/knowledge/import`，没有覆盖富 PDF 的 `/process`；00:34 的“零重启”仅为当时快照，已被后续故障推翻，不作为最终稳定验收。

修复候选将 PDF/Office 解码及 `/process` 的 OCR/表格/图表放入同一独立解析进程，单进程解析并发 1、384 MiB 内存预算、40 秒墙钟／Linux 25 秒 CPU、8 MiB 输出上限。Linux 同时设置地址空间硬限制，其他平台由父进程巡检工作进程树 RSS；两者强度不同。超限杀死并回收解析进程，返回既有 error 合同，不消耗后续模型调用。模型调用、租户上下文和数据库写入仍在主服务。

解析及模型阶段通过 `asyncio.to_thread` 执行，保留请求 ContextVar；AI 工具解析同样进入线程池，避免阻塞健康请求。PDF 文本、表格及图表扫描逐页释放缓存，超过 500 页明确要求拆分，文本最多 500,000 字并标记截断。没有 schema 或数据格式迁移。

只读复测原上传副本：26 秒左右受控返回资源上限错误，API 仍 active，重启数仍为 2。该证据证明故障被隔离，不代表原大文件已经成功完整分析。最终部署与公网合成真实上传压力回执另行记录；只有通过后才更新发布状态。

补充：原 PDF 共 312 页。相同边界内换用文字流解析器只读提取，12.39 秒取得 409,053 字／310 个有文字页。候选据此改为 PyPDF2 文字流优先、pdfplumber 回退；超过 50 页保留正文，但明确标记 `enrichment_incomplete`，提示按章节拆分后提取表格／图表几何结构。不会把这一降级标记为全部结构已识别。
